# 취업 포트폴리오 문서화 사전 점검

**점검일:** 2026-08-09  
**기준선:** `origin/main` PR #13 병합 상태 (`b1d63df`)  
**목적:** 문서를 전면 개편하기 전에, Benford Lens를 취업용 포트폴리오로 보여 주는 가장
효과적인 정보 구조와 보완 순서를 판단한다.

**후속 상태:** 사용자가 2026-08-09에 권장 구조와 MIT 라이선스를 승인했으며 TASK-037로
구현했다. 공개 문서는 네 종류로 정리하고 기존 개발 증거는 보존했다.

## 결론

Benford Lens는 이미 포트폴리오 소재로 사용할 수 있는 구현 깊이를 갖췄다. 핵심 분석,
데스크톱 UI, 다국어, 자동화 테스트, 성능 개선, macOS/Windows 패키징까지 하나의 제품
경계 안에서 연결되어 있기 때문이다.

다만 현재 저장소의 문서는 개발 과정 보존에는 강하지만, 채용 담당자가 짧은 시간 안에
"무슨 문제를 해결했고, 어떤 판단을 했으며, 무엇을 검증했는가"를 파악하기에는 진입점이
분산되어 있다. 따라서 기존 기록을 삭제하거나 전부 다시 쓰기보다 다음 원칙이 적절하다.

> 공개 포트폴리오 문서는 짧고 증거 중심으로 새 진입점을 만들고, `memory/`, `tasks/`,
> `reports/`의 상세 기록은 근거 자료로 보존한다.

## 현재 구현 기준선

| 영역 | 현재 상태 | 포트폴리오에서 보여 줄 가치 |
|------|-----------|------------------------------|
| 제품 기능 | v1.0 범위 구현 완료 | CSV/XLSX부터 분석·시각화·드릴다운·HTML 보고서까지 이어지는 완결된 사용자 흐름 |
| 통계/분석 | 첫째·둘째·결합 모드, MAD/Chi-square/KS | UI와 분리된 분석 계층, 통계적 정확성 테스트, 자동 판정 대신 사용자 판단을 존중한 설계 |
| 개인정보 보호 | 전체 로컬 처리, 계정·텔레메트리·네트워크 분석 없음 | 요구사항을 아키텍처 제약으로 일관되게 구현한 사례 |
| UX | 명시적 선택, 전처리 미리보기, 반응형 결과, 차트 드릴다운 | 비전문가용 데스크톱 워크플로 설계 및 다국어 레이아웃 문제 해결 |
| 국제화 | 영어 + 6개 번역 언어 | 번역 카탈로그 완전성, 플레이스홀더, 실제 UI 전환 회귀 테스트 |
| 품질 | Ruff/format/mypy 통과, 241 tests | 분석·UI·보고서·번역을 아우르는 자동화 검증 |
| 성능 | 10만 행 기준 기록상 30.0–31.8% 개선 | 프로파일링으로 중복 자릿수 추출을 제거한 정량적 개선 사례 |
| 배포 | macOS arm64 후보, Windows x64 ZIP/MSI 후보 | PyInstaller, 아이콘/메타데이터, 설치·실행·제거 검증 경험 |
| 공개 릴리스 | 아직 미게시 | 서명·공증·클린 머신 검증이 남았음을 투명하게 표시해야 함 |

2026-08-09 macOS 로컬 재검증 결과는 Ruff lint, Ruff format, mypy 22개 소스 파일,
pytest 241개 테스트 모두 통과다. 같은 기준선의 GitHub Actions도 성공했다. 기존 95.00%
커버리지는 2026-08-06 M3 기준 측정치이므로, 현재 커버리지처럼 표시하지 않는다.

## 포트폴리오 강점

1. **작동하는 제품 단위의 완결성**  
   단일 알고리즘 데모가 아니라 파일 입력, 전처리, 통계, 시각화, 원본 행 탐색, 보고서,
   배포까지 실제 사용 흐름이 이어진다.

2. **제약을 설계로 연결한 흔적**  
   로컬 전용 처리, 원본 파일 비수정, 명시적 열 선택, 중립적 결과 표현이 코드·테스트·문서에
   반복해서 반영되어 있다. 단순 기능 수보다 설계 판단을 설명하기 좋은 지점이다.

3. **측정 가능한 개선 사례**  
   10만 행 성능 개선, 241개 테스트, 7개 UI 언어, Windows 설치/제거 검증처럼 숫자로
   확인 가능한 근거가 있다.

4. **문제 해결 서사가 분명함**  
   결합 분석의 상태 일관성, 작은 화면에서의 차트 압축, Windows CJK 글꼴, 러시아어 툴바
   폭, 차트 위 휠 스크롤 등 구체적인 문제와 해결 과정이 남아 있다.

## 문서 격차와 우선순위

### P0 — 공개 전에 반드시 결정하거나 바로잡을 항목

- **라이선스 파일 부재:** README는 오픈소스라고 설명하지만 저장소 루트에 `LICENSE`가
  없다. 라이선스 선택은 권리자의 판단이므로 문서 개편 전에 사용자가 직접 결정해야 한다.
- **공개 릴리스 부재:** 소스 버전은 1.0.0이지만 태그와 GitHub Release가 없다. 서명되지
  않은 후보를 정식 배포본으로 표현하지 않는다.
- **릴리스 사실관계:** 존재하지 않는 릴리스 링크는 제거하고 현재 상태를 release candidate로
  명시했다.

### P1 — 포트폴리오 전달력을 크게 높이는 항목

- 대표 화면 이미지 또는 짧은 GIF가 없다. 합성 데이터만 사용해 파일 선택 전, 결합 분석,
  드릴다운/통계 상세의 세 장면을 우선 촬영한다.
- README가 기능과 실행법 중심이라 문제, 대상 사용자, 핵심 설계 판단, 본인 기여, 결과 수치가
  한 흐름으로 연결되지 않는다.
- 아키텍처와 검증 근거가 `memory/` 및 여러 `reports/`에 흩어져 있다. 채용 검토자가 따라갈
  수 있는 2–3개의 공개 문서 링크가 필요하다.
- 한국어 채용 환경에서 바로 읽을 수 있는 한국어 진입점이 없다. 영어 README를 기본으로
  유지하되 `README.ko.md`를 같은 구조로 제공하는 편이 적절하다.

### P2 — 신뢰도와 유지보수성을 높이는 항목

- `tech-stack.md`와 `dependencies.md` 일부가 실제 버전/현재 다국어 범위보다 오래됐다.
- `memory/session 2.md` 같은 내부 인계 파일과 과거 계획이 공개 독자에게는 소음이 될 수 있다.
  삭제할 필요는 없지만 README의 주 탐색 경로에서는 분리한다.
- 기여 가이드와 공개 보안/개인정보 보호 설명이 없다. 오픈소스로 공개할 때
  `CONTRIBUTING.md`와 간결한 `SECURITY.md` 또는 privacy 문서를 추가할 가치가 있다.
- CI는 커버리지를 강제하지 않는다. 최신 커버리지를 배지로 표시하려면 먼저 재현 가능한
  측정과 CI 기준을 마련해야 한다.

## 권장 공개 문서 구조

문서 수를 늘리는 것이 목적이 아니다. 다음 정도면 채용 검토자, 사용자, 개발자의 경로를
분리하면서도 관리 가능한 범위다.

```text
README.md                      영어 포트폴리오 랜딩 페이지
README.ko.md                   동일 구조의 한국어 진입점
LICENSE                        사용자가 선택한 실제 오픈소스 라이선스
CONTRIBUTING.md                개발 환경, 검사, PR 원칙
docs/
├── portfolio-case-study.md    문제 → 제약 → 판단 → 구현 → 결과 → 회고
├── architecture.md            계층, 데이터 흐름, 주요 ADR 요약
├── verification.md            테스트 범위, 성능 측정, 패키징 검증, 남은 경계
├── user-guide.md              파일 열기부터 보고서 저장까지의 사용자 흐름
└── assets/                    합성 데이터로 촬영한 스크린샷/GIF
```

기존 `memory/`, `tasks/`, `reports/`는 개발 증거와 이력으로 유지한다. 과거
`docs/superpowers/` 계획·설계 기록도 `reports/development/`로 옮겨 보존한다. README에서는
이들을 한꺼번에 노출하지 말고, 공개 문서가 필요한 근거만 선택적으로 링크한다.

## README 권장 순서

1. 한 문장 가치 제안 + 로컬 전용 처리 강조
2. 대표 스크린샷/GIF
3. 해결하려는 문제와 대상 사용자
4. 핵심 기능 5–7개
5. 기술적 하이라이트와 정량 근거
6. 작은 아키텍처 다이어그램
7. 빠른 실행 방법
8. 현재 배포 상태와 제한 사항
9. 사례 연구·아키텍처·검증 문서 링크
10. 라이선스와 기여 방법

내부 작업 수, 에이전트 역할, 세션 로그를 전면에 두기보다 사용자가 체감하는 결과와 본인이
내린 기술적 판단을 먼저 보여 주는 편이 좋다.

## 사례 연구에서 강조할 세 가지 이야기

### 1. 결합 분석의 일관성

첫째·둘째 자리 분석을 별도 파이프라인으로 복제하지 않고 한 번의 전처리와 불변 스냅샷을
공유했다. 이는 중복을 줄인 이야기보다 "두 결과가 동일한 사용자 선택과 데이터 상태를
설명하도록 보장했다"는 데이터 일관성 이야기로 표현한다.

### 2. 측정으로 찾은 성능 병목

10만 행에서 반복된 자릿수 추출이 병목임을 확인하고 한 번 추출한 정렬 결과를 분석과
드릴다운이 공유하도록 바꿨다. 전후 중앙값과 측정 조건을 함께 제시하되 사용자 환경에서의
성능 보장으로 과장하지 않는다.

### 3. 다국어 데스크톱 UX의 실제 문제 해결

번역 문자열만 추가한 것이 아니라 CJK 글꼴 선택, 러시아어 툴바 폭, 작은 화면 스크롤,
차트 위 휠 이벤트까지 회귀 테스트로 다뤘다. 국제화와 레이아웃 안정성을 함께 해결한 사례다.

## 정리 실행 순서

1. **사실과 정책 확정:** 라이선스 선택, 목표 지원 플랫폼, 공개 릴리스 범위를 결정한다.
2. **시각 자료 확보:** 합성 데이터로 대표 화면과 짧은 데모를 만든다.
3. **README 재작성:** 영어 기본본을 먼저 완성하고 한국어판을 같은 구조로 맞춘다.
4. **사례 연구 작성:** 위 세 가지 이야기와 제품 제약을 하나의 흐름으로 정리한다.
5. **근거 문서 압축:** 아키텍처와 검증 문서가 기존 ADR/보고서를 가리키게 한다.
6. **공개 품질 점검:** 링크, 실행 절차, 중립적 표현, 개인정보 보호, 릴리스 상태를 재검증한다.

## 하지 않는 편이 좋은 것

- 내부 기록을 보기 좋게 만들기 위해 삭제하거나 커밋 이력을 재작성하지 않는다.
- 공개되지 않은 릴리스, 서명 상태, 현재 커버리지 수치를 완료된 것처럼 표현하지 않는다.
- 실제 사용자 CSV/XLSX나 그 파생 값을 스크린샷·샘플·벤치마크에 사용하지 않는다.
- 기능 목록을 더 늘리는 것으로 포트폴리오 완성도를 해결하려 하지 않는다.
- AI 개발 하네스를 주된 성과처럼 전면에 두지 않는다. 제품 판단과 검증 결과가 중심이다.

## 다음 단계의 완료 기준

- README 첫 화면만으로 제품 목적, 로컬 처리, 대표 기능, 현재 배포 상태를 이해할 수 있다.
- 한 개의 사례 연구에서 최소 세 가지 기술적 판단과 정량 결과를 확인할 수 있다.
- 스크린샷과 데모는 합성 데이터만 사용한다.
- 모든 공개 주장에 코드, 테스트, ADR 또는 검증 보고서 근거가 있다.
- 라이선스와 릴리스 상태가 실제 저장소 상태와 일치한다.
